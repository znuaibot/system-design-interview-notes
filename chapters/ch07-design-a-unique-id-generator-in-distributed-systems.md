# Chapter 7: Design a Unique ID Generator in Distributed Systems

## Core Idea
唯一 ID 方案由唯一性、可排序性、位宽、吞吐和中心依赖五个约束共同决定；Snowflake 用"时间戳+节点+序列"位段在去中心化前提下同时满足这些约束。

## Frameworks Introduced
- **四方案淘汰赛**：Multi-Master auto_increment → UUID → Ticket Server → Snowflake，逐个用约束检验淘汰。
  - When to use：任何"分布式 ID 怎么生成"的问题。
  - How：对每个方案检查五条需求（唯一、64 位、按时间可排序、>10k/s、无单点），不满足即淘汰，最后剩下的就是答案。

## Key Concepts
- **需求基线**：ID 唯一、数值型、64 位、随时间递增（不要求严格 +1）、可按日期排序、吞吐 >10,000/s。
- **Multi-Master Replication**：各数据库用 auto_increment 步长 k（k 台服务器）各自发号；缺陷：难跨数据中心、ID 不随时间单调、加减机器要重排步长。
- **UUID**：128 位，各服务器独立生成无需协调；缺陷：超 64 位、不按时间排序、可能非数值。
- **Ticket Server**：中心化数据库逐号递增发号；优点是简单且严格递增；缺陷是单点故障和多服务器同步压力。
- **Twitter Snowflake**：64 位 = 1 符号位（恒 0）+ 41 位毫秒时间戳（自定义 epoch，Twitter 为 1288834974657，即 2010-11-04）+ 5 位数据中心 ID（32 个）+ 5 位机器 ID（32 台）+ 12 位序列号（同毫秒 4096 个，每毫秒归零）。
- **Snowflake 容量**：单机 4096×1000≈409 万/秒，远超 1 万/秒需求；32×32=1024 台机器；时间趋势递增、无中心节点。
- **Clock Synchronization**：Snowflake 依赖时钟单调，用 NTP 控制漂移。
- **Section Length Tuning**：位段可按业务调整——节点少就缩节点位、寿命长就扩时间位。

## Decision Rules
1. 只需唯一、不在乎排序和位宽 → UUID（最简单）
2. 需要趋势递增 + 高吞吐 + 去中心化 → Snowflake（默认答案）
3. 需要严格递增且规模小 → Ticket Server，但必须解决中心可用性
4. 位段分配先算业务寿命（时间位）和最大节点数（节点位），余量给序列位
5. ID 生成器是 mission-critical，要有冗余与故障切换

## Mental Models
- **位段是资源预算**：64 位里每一位都在时间范围、节点规模、单机吞吐之间做分配，先算需求再分位。
- **约束淘汰法**：不要直接说"用 Snowflake"，先展示三个方案各自死在哪条约束上。
- **时钟是隐藏依赖**：所有基于时间戳的方案都要回答"时钟回拨怎么办"。

## Anti-patterns
- **时钟回拨无策略**：回拨期间生成的 ID 可能重复或乱序——短回拨应等待，长回拨应隔离节点并告警。
- **节点 ID 靠人工分配**：机器替换或扩容时两个节点拿到同一 ID，产生重复号段。
- **位段拍脑袋定长**：时间位不够系统提前"过期"，节点位不够无法扩容。
- **用数据库自增扛分布式发号**：单点和同步瓶颈随规模放大。

## Worked Example
按 Snowflake 分配 64 位：业务预计存活 20 年，2^41 毫秒≈69 年够 → 时间位 41；最大 100 台机器，5+5 位（1024）够 → 节点位 10；单机峰值 10k/s，同毫秒只需 10 个 → 12 位序列（4096/ms）绰绰有余。时钟策略：NTP 同步 + 检测到回拨 <5ms 则自旋等待，>5ms 则停用该机器发号并告警。节点 ID 用配置中心或启动时租约分配，避免人工撞号。

## Interview Lens
1. 开场复述五条需求约束，让后续淘汰有据可依。
2. 把四方案逐一过约束：multi-master 死在排序和扩展，UUID 死在位宽和排序，ticket server 死在单点——Snowflake 全过。
3. 能现场默写 Snowflake 位段（1/41/5/5/12）和各段容量。
4. 主动提出时钟回拨与节点 ID 分配两个工程细节，显示落地经验。

## Practitioner Checklist
- [ ] 五条需求约束逐条有对应论证
- [ ] 位段长度按寿命/节点数/吞吐计算过
- [ ] 时钟同步与回拨策略明确
- [ ] 节点 ID 有自动分配机制
- [ ] ID 生成器有冗余与切换方案

## Key Takeaways
1. UUID 解决唯一性，Snowflake 同时解决唯一、排序和吞吐
2. Snowflake 位段 = 1+41+5+5+12，可按业务调参
3. Ticket server 适合小规模严格递增，代价是单点
4. 时钟同步与节点 ID 分配是 Snowflake 的两个隐藏工程点
