# Chapter 5: Design Consistent Hashing

## Core Idea
一致性哈希把节点和键映射到同一个环上，使节点增删只迁移相邻区间的少量键；虚拟节点解决分布不均，是水平扩展的分片基石。

## Frameworks Introduced
- **环模型三步走**：hash space 成环 → 节点上环 → 键顺时针找节点。
  - When to use：缓存集群、KV 存储、任何节点数会动态变化的分片场景。
  - How：用同一哈希函数（如 SHA-1，空间 0..2^160-1）映射节点 IP 和键；键沿环顺时针找到第一个节点即为归属。
- **受影响键范围分析**：加节点 → 新节点与其前驱之间的键迁移过来；删节点 → 该节点与前驱之间的键转给顺时针下一节点。
  - When to use：评估扩缩容的数据迁移成本。
  - How：画出环，标出变更节点，圈出受影响的弧段即可估算迁移量。

## Key Concepts
- **Rehashing Problem**：传统 hash(key)%N 在 N 变化时几乎所有键都要重映射，导致缓存集体失效和节点过载。
- **Hash Ring**：哈希值首尾相接形成的环（0 到 2^160-1），节点和键都映射到环上。
- **Server Lookup**：键沿环顺时针走，遇到的第一个服务器就是它的归属节点。
- **Virtual Nodes**：每台物理机在环上放多个虚拟节点；虚拟节点越多，键分布标准差越小，负载越均衡；虚拟节点数可按机器容量差异化配置。
- **Uneven Partition / Non-uniform Distribution**：基础一致性哈希的两个缺陷——分区大小不均、键分布不均，靠虚拟节点解决。
- **Affected Keys**：节点变更时只需要重映射环上一段弧内的键，这是迁移成本可控的关键。

## Decision Rules
1. 节点增删频繁 → 用一致性哈希替代 hash%N
2. 分布不够均匀 → 增加虚拟节点数量
3. 机器容量异构 → 大容量机器配更多虚拟节点
4. 需要预估扩缩容成本 → 只算受影响弧段内的键

## Mental Models
- **把变更成本局部化**：好的分片方案让"加一台机器"只影响 1/N 的数据，而不是全量。
- **均匀是统计出来的**：虚拟节点数量与分布标准差成反比，均衡度可以用数字论证。
- **环是抽象不是实现**：实际系统里环只是一张路由表，重点是它给出的迁移边界。

## Anti-patterns
- **直接 hash(key)%N**：扩缩容触发全量重映射，缓存命中率瞬间归零。
- **物理节点太少不加虚拟节点**：数据严重倾斜，部分节点过载。
- **只谈分布均匀不谈热点键**：即使哈希完美，单个超级热键仍会打垮一个节点。

## Worked Example
三台缓存服务器 s1/s2/s3 上环，每台放 100–200 个虚拟节点。键 k 哈希后顺时针落到 s2。现在加入 s4：只有 s3→s4 弧段内的键从 s3 迁到 s4，其余键不动。验证均衡性：统计每个物理节点的虚拟节点覆盖弧长占比与请求量，两者偏差应随虚拟节点数增加而收敛。若某业务键天然集中（如明星用户），需要额外的热点拆分手段，环本身解决不了。

## Interview Lens
1. 先用 hash%N 的 rehashing 问题开场，再引出一致性哈希——展示"为什么需要它"。
2. 画环 + 顺时针查找是最核心的表达，务必手绘。
3. 主动提出两个缺陷（分区不均、分布不均）并用虚拟节点解决——这是深挖考点。
4. 报真实应用：Amazon DynamoDB、Cassandra、Discord、Akamai、Maglev，证明工程落地认知。

## Practitioner Checklist
- [ ] 哈希函数对节点和键使用同一个
- [ ] 虚拟节点数量有依据（容量比例、标准差目标）
- [ ] 扩缩容迁移量可按弧段估算
- [ ] 热点键有环之外的应对方案
- [ ] 节点上下线有自动路由更新机制

## Key Takeaways
1. 一致性哈希让节点增删只迁移 1/N 量级的键
2. 虚拟节点是负载均衡与异构容量适配的标准解
3. 三大收益：最小化重分布、水平扩展、缓解热点
4. DynamoDB/Cassandra/Akamai/Maglev 都建立在此之上
